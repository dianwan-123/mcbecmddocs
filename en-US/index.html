Preface: Build Your Own Game World with Commands#

In Minecraft (Bedrock Edition), commands are like a magical programming language designed specifically for conversing with the game engine. Whether you want to build an automated shop for your survival world, create an engaging puzzle or adventure map, or understand the underlying logic behind sophisticated server mechanics, commands are an indispensable and powerful tool.

Many people find commands intimidating because tutorials online often present cryptic lines of code or overwhelm readers with convoluted jargon. This book uses clear, beginner-friendly language combined with practical case studies to guide you step by step from scratch—starting with command blocks, mastering the modern /execute system, and building scoreboard mechanics, all the way to binary decomposition and cutting-edge nx-Tree (MEF / execute fork) techniques.

Chapter 1　Getting to Know Command Blocks: Turning Manual Commands into Automated Machines#

Moving Beyond Manual Command Input#

Typing /gamemode c or /time set day in the chat window only executes a single command once. When designing custom maps where you must continuously track player positions or trigger cutscenes the moment a player steps into an area, manual entry falls short. For this, we need a tool capable of executing commands automatically: the Command Block.

The Three Colors and Core Settings of Command Blocks#

Command blocks cannot be found in the Creative inventory; you must obtain them via a command:

Place the block and right-click (or tap) to open its interface. You will see several key configuration options:

1. Three Block Types (Identified by Color)#

  • Impulse (Orange): Executes once whenever it receives a redstone signal (such as pressing a button).
  • Chain (Green): Does not trigger on its own; it must be placed directly in front of another command block pointing into it. Once the preceding block executes, the chain block executes immediately down the line of arrows.
  • Repeat (Purple): As long as it remains active, it executes continuously at a rate of 20 times per second (once every game tick).

2. Conditions and Activation Modes#

  • Conditional vs. Unconditional:
    • Unconditional: Runs regardless of whether the preceding block succeeded.
    • Conditional (marked by an indented notch on the arrow's tail): Triggers only if the preceding command block executed successfully.
  • Always Active vs. Needs Redstone:
    • Always Active: Remains continuously powered without needing redstone dust or levers (commonly used for Repeat and Chain blocks).
    • Needs Redstone: Requires an adjacent active redstone signal (levers, buttons, redstone torches) to function.
  • Tick Delay:
    • Accepts an integer value. For example, entering 20 makes a Repeat block execute once per second instead of every tick (1 second ≈ 20 game ticks).

Construction Notes and Troubleshooting#

  1. Verify Arrow Directions: Chain blocks must be pointed at directly from behind by the previous block's arrow. If an arrow is misaligned, the chain stops at the break point.
  2. Prevent Chat Spam: Before building systems, run these two commands in chat to suppress command block execution logs:
    • /gamerule commandblockoutput false
    • /gamerule sendcommandfeedback false
  3. Keep-Loaded Regions (Ticking Areas): When players travel far away, chunks unload and command blocks halt. Run /tickingarea add circle ~~~ 4 logic_core at your command center so your systems run uninterrupted anywhere in the world.

Chapter 2　Targeting Entities and Finding Positions: Target Selectors and Coordinate Systems#

How to Precisely Target Any Entity#

Giving a sword to a specific player is as simple as /give Steve iron_sword. But what if multiple players have different names, or you want to target the player with the lowest health, or apply rewards/penalties to the nearest monster? For this, you need Target Selectors and 3D Coordinates.

Selector Variables, Filter Arguments, and the Three Coordinate Systems#

1. Standard Target Selector Variables#

  • @a: All players (including deceased players awaiting respawn).
  • @p: Nearest player relative to the execution origin.
  • @r: Random player (can select random entities when paired with type arguments).
  • @e: All entities (players, mobs, dropped items, armor stands, etc.).
  • @s: The executing entity itself (whoever is currently running the command).

2. Filter Arguments (Inside Square Brackets)#

Appending [] after a selector variable lets you add comma-separated filtering criteria:

Filter CategoryExampleDescription
Type Filteringtype=cow, type=!playerSelects only cows; prefixing ! excludes players
Count Limitsc=1, c=3Selects the nearest 1 or first 3 targets
Spherical Radiusr=5, rm=2r=5 targets within 5 blocks; rm=2 excludes within 2 blocks
Volume Bounding Boxx=0,y=64,z=0,dx=5,dy=2,dz=5Defines a 5x2x5 box offset from (0,64,0)
Tag Filteringtag=vip, tag=!badSelects entities matching or lacking specific tags
Item Detectionhasitem={item=apple,quantity=1..}Detects players holding at least 1 apple

3. The Three Coordinate Systems#

  • Absolute Coordinates (Fixed World Positions): e.g., 100 64 -20, referencing a fixed point in the world.
  • Relative Coordinates (~): Offsets relative to the current execution origin. ~ ~2 ~ denotes 2 blocks above the current origin.
  • Local View Coordinates (^): Offsets relative to the entity's line of sight, formatted as ^left/right ^up/down ^forward/backward. ^ ^ ^3 represents 3 blocks directly in front of the line of sight.

Critical Nuances and Common Traps#

  1. Never Use Unfiltered @e Carelessly: Running a bare /kill @e deletes every painting, minecart, armor stand, and item frame across the world. Always filter using type= or a distance range r=.
  2. Player Eye Height: In Bedrock Edition, a player's eye height is approximately 1.62 blocks above their feet (relative coordinate ~ ~1.62 ~).

Chapter 3　The Brain of Commands: The Modern /execute Context Pipeline#

Why the Legacy execute Was Insufficient#

The legacy syntax /execute <target> <x y z> <command> tightly bound the executor and the execution position together. Performing operations like making a skeleton face a player, shifting execution to eye height, or running only in rain required cumbersome workarounds. The modern /execute syntax functions like a modular assembly pipeline, making logic clear and immensely flexible.

The Context Pipeline and Modifier Subcommands#

The modern /execute syntax follows this pipeline structure:

1. Modifying Identity and Position#

  • as <target>: Changes who the executor is (sets @s to the target).
  • at <target>: Inherits the target's current position, rotation, and dimension.
  • positioned <x y z> or positioned as <target>: Changes position only, keeping rotation unchanged.
  • anchored (eyes|feet): Anchors local coordinate offsets to the eyes or feet.
  • facing <x y z> or facing entity <target> (eyes|feet): Orients rotation toward a specified point or entity.
  • align xyz: Floors coordinate decimals to align with the block grid.

2. Conditional Subcommands#

  • if|unless entity <target>: Continues only if matching entities exist / do not exist.
  • if|unless block <x y z> <block_name>: Continues only if a block matches / does not match.
  • if|unless score <target> <objective> matches <range>: Checks whether a scoreboard value satisfies a condition.

Common Combinations and Practical Examples#

Example 1: Trigger Effect on Block Step#

Example 2: Lightning Strike on Arrow Impact#

Common Pitfalls#

  1. Confusing as and at:
    • Writing as @a sets @s to the player, but the execution position remains at the command block!
    • To execute at the player's position with their identity, write as @a at @s.
  2. Conditional Pipeline Breakage: If an upstream condition fails (such as if block not matching), the entire downstream pipeline halts immediately without errors or running the trailing command.

Chapter 4　Logical Evaluation Techniques: Implementing "OR" and Complex Branching#

How to Handle "OR" When Native Selectors Default to "AND"#

Map design frequently calls for disjunctive conditions: "Allow entry if a player has an iron sword OR a diamond sword," or "Lock the door if anyone in the team is unready." Native selectors evaluate multiple conditions as simultaneous requirements (AND logic). How do we implement "OR" and "NAND" branching?

Constructing Logic Gates via Command Pipelines#

Using /execute unless (conditional negation) paired with logical exclusion, we can construct standard Boolean logic gates:

Logic Gate Reference#

  • AND Logic: Both conditions must be satisfied.

  • NOT Logic: Executes only if a condition is absent.

  • OR Logic: Executes if either A or B is satisfied (De Morgan's law: unless both NOT A and NOT B hold, execute).

  • XOR Logic: Exactly one condition must be true; fails if both or neither are met.

2. The Nine Scoreboard Operations (operation)#

Syntax: /scoreboard players operation <receiver> <objective> <operator> <contributor> <objective>

OperatorFunctionDescription & Example
+=AdditionA money += B money (Adds B's score to A)
-=SubtractionA money -= B money (Subtracts B's score from A)
*=MultiplicationA money *= B money (Multiplies A's score by B)
/=Integer DivisionA money /= B money (Divides A by B, discarding the remainder)
%=Modulo (Remainder)A money %= B money (Computes remainder of A / B; ideal for cyclical timers)
=AssignmentA money = B money (Copies B's score into A)
<Minimum ValueA money < B money (Stores the lesser of A and B into A)
>Maximum ValueA money > B money (Stores the greater of A and B into A)
><Swap ValuesA money >< B money (Swaps the scores of A and B)

3. Building Multi-Period Clocks with Modulo (%=)#

By incrementing a single timer variable main_timer by 1 every tick and using modulo operations, a single command chain can manage multiple recurring schedules simultaneously:

  • 30 seconds (600 ticks): main_timer % 600 == 0
  • 10 minutes (12000 ticks): main_timer % 12000 == 0

Numerical Computing Tips#

  1. Integer Division Discards Decimals: In scoreboard arithmetic, 5 / 2 yields 2, not 2.5. When calculating percentages (such as current health over maximum health), multiply by 100 first before dividing by max health!
  2. The Wildcard *: The wildcard * acts on all entities and dummy names ever recorded in that objective (including offline players). When targeting active online players, prioritize using @a.

Chapter 6　State Detection Techniques: Detecting Sneaking, Sleeping, Line of Sight, and Weather#

Detecting Player Actions and Environmental States#

Beyond coordinates and scores, map logic frequently requires detecting real-time player behaviors: Is the player sneaking? Are they asleep in bed? Which mob are their eyes locked onto? Is it currently raining? By combining hitbox height deltas, sightline reflection geometry, and block physics, we can detect all of these without external addons.

Hitbox Height Offsets and Sightline Reflection Geometry#

1. Hitbox Heights Across Poses#

Following the short-sneaking update in Bedrock 1.20.10, player hitbox heights differ distinctively across poses:

  • Standing Height: ~1.8 blocks
  • Sneaking Height: ~1.5 blocks
  • Crawling / Swimming / Elytra Gliding Height: ~0.6 blocks
  • Sleeping Height: ~0.2 blocks

2. Look Detection Geometry#

How do we verify whether a player is looking directly at a target?

  • Start from the player's eyes, look toward the target's direction, and advance 1 block (facing <target> ... positioned ^^^1).
  • Restore the player's own view rotation, and step backward 1 block (rotated as @s ... positioned ^^^-1).
  • If the player is looking directly at the target, these forward and backward steps cancel out, returning to the origin. Testing whether the end position is within 0.2 blocks of the player (if entity @s[r=0.2]) reliably confirms direct line of sight!

Chapter 8　Interface and Visual Magic: Screen Rich Text and Custom Display Blocks#

Professional Visuals in Vanilla Commands#

Plain white text can feel uninspired. How do you create polished title screens, health bars, and currency HUDs? Can you create miniature blocks or custom floating furniture without installing external 3D resource packs?

Rawtext Structure and Maxed Armor Stand Display Blocks (MBE)#

1. The Three Core Components of JSON Rich Text (rawtext)#

Used with /tellraw and /titleraw:

  • text: Plain text strings with formatting color codes (e.g., §a, §e).
  • selector: Dynamically inserts targeted entity names (e.g., {"selector": "@p"}).
  • score: Dynamically renders scoreboard numeric values into strings.

Pioneered by community creator Maxed_Out:

  • Name an armor stand Grumm (rendering it upside down).
  • Set it into a specific idle pose holding the desired block item.
  • Play /playanimation using zombie arm animations and ghast scale transformations to enlarge and align the held item into a crisp, standalone "custom block model."

Chapter 9　Algorithm Optimization and Advanced Techniques: Binary Decomposition and nx-Tree Multi-Forking#

Executing Hundreds of Operations in a Handful of Commands#

Suppose you are designing a bulk sell chest where a player might deposit anywhere from 1 to 64 pieces of bread. Do you write 64 individual commands to test every count? If you want to spawn a full 3D sphere of particles above a player instantly, do you need hundreds of command blocks? Using Binary Decomposition and nx-Tree (MEF / Multi-Execute Fork), we can achieve massive exponential efficiency in minimal commands.

Binary Decomposition and the nx-Tree Forking Model#

1. Binary Decomposition Principle#

Any integer between 1 and 64 can be uniquely represented as a sum of at most 7 powers of 2:

64, 32, 16, 8, 4, 2, 1

For example, 50 loaves of bread: 50 = 32 + 16 + 2.
By evaluating these 7 thresholds in descending order, we can process and convert any item count into currency in just 7 steps—orders of magnitude faster than deducting items one by one.

2. nx-Tree (MEF / Multi-Execute Fork) Principle#

In /execute, when a selector targets n entities, execution splits into n separate execution branches.
Chaining x multi-entity selectors sequentially causes the branch count to multiply exponentially like the canopy of a tree:

\text{Total Execution Instances} = n^x

By placing two reference boats with designated rotation offsets and leveraging nx-Tree (MEF) to multiply rotation angles within a single command, you can generate thousands of spatial computation points within a single tick!

Server Performance and Anti-Freeze Guidelines#

  1. Always Limit Selector Counts (c=) in nx-Trees: Every nested selector in an nx-Tree (MEF) chain must include an exact count limit such as c=2. Using an unfiltered @e when dozens of mobs are nearby can spawn hundreds of thousands of branches instantly, crashing the server.
  2. Isolate Reference Entities: Keep the two positioning boats in an enclosed bedrock chamber inside a ticking area so they cannot be displaced by water currents or destroyed by mobs.

3. Why This Works#

  • The initial segment uses rotated as @e[tag=boat_rot] (2 boats) for binary branching, combined with positioned ^1^^ to split into 32 regular polygon vertices on the horizontal plane.
  • Next, using the pitch angles of the boats and positioned ^^^1.414 (\sqrt{2} unit length), branches expand upward and downward, stretching the 2D ring into a 3D spherical latitude/longitude wireframe.
