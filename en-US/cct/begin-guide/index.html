The Guide For Beginner

CCT and MEF#

The Complete Coordinate Calculation Tutorial for Minecraft Bedrock Edition

About This Book#

In the pure-command environment of Minecraft Bedrock Edition (MCBE), there are two independent techniques.

CCT (Coordinates Calculation Theory / Coordinate Computation Technique, historically known in the community as the "Large-Number Compass") solves the problem of computation. It uses positioned, facing, and rotated to construct virtual positions and rotations, leveraging a very large distance H to make the game engine act as a calculator—computing midpoints, mirrored points, rotated points, as well as squaring, multiplication, and division. When a CCT command finishes running, it outputs one single point.

MEF (Multi-Execute Fork, commonly known in the community as the "n-ary tree") solves the problem of duplication. It exploits the property that when a target selector matches multiple entities, execution forks along multiple paths, allowing a single command to execute simultaneously across hundreds or thousands of positions. MEF performs no calculations on its own; it simply multiplies execution paths.

In a single sentence: CCT computes a single point; MEF turns a single computation into many points.

This book decouples the two. Chapters 1 through 5 cover CCT, where all commands strictly use c=1 (one execution path, one point per command). Chapter 6 covers MEF. Chapter 7 covers combining both techniques. Chapter 8 translates the geometric intuition into rigorous algebraic expressions, followed by a formula reference in the Appendix.

The Most Critical Correction in This Edition

In Bedrock Edition, armor stands do not preserve pitch. This means armor stands can only represent horizontal orientations; purely using armor stands cannot achieve 3D space traversal. Wherever vertical components are required, the reference entities must be switched to boats.

This is not a minor detail—it dictates which entity type must be used for each command. Section 1.4 is dedicated to this topic, and the 3D cube in Chapter 6 is built entirely upon it.

Everything before Chapter 6 requires only junior-high math: similar triangles, the Pythagorean theorem, the difference-of-squares formula, and the inscribed angle theorem. Chapter 8 introduces vectors and matrices.

All commands in this book should be tested with particles first to verify their computed positions before swapping in other execution actions.

Chapter 1　The Coordinate Syntax of execute#

At bottom, CCT does only three things: change the origin, change the axes, and move along the axes. This chapter clarifies the syntax for these three actions and resolves a practical question: which reference entities should be used?

1.1 Three coordinate systems#

Absolute Coordinates specify fixed world positions directly:

Regardless of where you are or which way you look, the destination is identical.

Relative Coordinates ~ are offsets measured relative to the current execution origin:

X plus 5, Y plus 2, Z minus 3. A bare ~ equals ~0, so ~ ~1 ~ means "move 1 block upward from the current origin."

Local Coordinates ^ are offsets measured relative to the current view rotation. The three parameters are always ordered:

One strict rule: Within a single 3-axis parameter group, ~ and absolute coordinates can be mixed, but ^ cannot be mixed with either.

If you need to combine them, split the operation into two subcommands:

First shift upward by 1 block in world coordinates, then advance 3 blocks along the local line of sight. Subcommands apply sequentially, so splitting them has no side effects.

1.2 Rotation: yaw and pitch#

Rotation is written as two numbers:

yaw is the horizontal heading:

Because the direction of ^ is determined entirely by rotation, ^ ^ ^1 is affected by pitch and is not necessarily horizontally forward. Looking up by 30° makes it move forward and upward simultaneously.

Three key observations should be remembered now, as they are used throughout this book:

Observation 1: The local left direction is always horizontal. The left vector depends solely on yaw; pitch has no effect on it. Thus positioned ^2 ^ ^ is always a pure horizontal translation.

Observation 2: Modifying yaw does not affect the vertical component of the forward direction. The vertical component of the forward vector depends solely on pitch. Therefore, rotated ~180 ~ (adding 180° to yaw) flips the horizontal components of the forward direction while leaving the vertical component invariant.

Observation 3: When pitch = 0, the forward direction is strictly horizontal. Thus rotated ~ 0 flattens any view rotation into a pure horizontal plane.

Chapter 8 provides matrix proofs for these three properties. For now, remember them as rules.

1.3 Five core subcommands#

positioned: modifies position only#

positioned as has an easily overlooked property: it moves position only; it does not copy rotation. After executing it, you stand at entity A's position, but your orientation remains unchanged. The nested circle in Chapter 7 specifically relies on this.

facing: modifies rotation only#

feet targets the feet and eyes targets the eyes. Never mix these within the same formula—they differ by ~1.62 blocks, which will distort small-scale geometric figures.

facing is the engine of CCT, as Chapter 2 will explain.

rotated: modifies rotation directly via angles#

Four notations must be strictly distinguished—confusing them will distort your geometry:

Two High-Frequency Combinations:

align: coordinate flooring#

Floors coordinates to block-grid integers along specified axes, modifying position only. When current X is 3.7, align x floors it to 3. Combined with large-number translation, this implements modulo operations and periodic wrapping (used in Appendix D.3 for trigonometric functions).

at: modifies both position and rotation#

Transfers both origin and orientation to the target entity. CCT commands frequently use this as the starting anchor.

1.4 Reference entities: armor stands vs. boats#

This section is the most practical guide in the book.

Armor stands do not preserve pitch#

In Bedrock Edition, armor stands only store yaw. You can run /tp with a pitch argument on an armor stand, but that value is ignored—the armor stand's rotation data structure does not retain pitch.

Direct consequence: The directions an armor stand can represent are strictly confined to the horizontal circle.

Deducing further: positioned ^ ^ ^d moves forward, and positioned ^d ^ ^ moves left. When pitch = 0, both directions lie entirely within the horizontal plane. Therefore:

Using purely armor stands, no matter how you combine them, you cannot leave the horizontal plane. 3D spatial traversal is impossible.

Yaw is sufficient for the X and Z axes, but the Y axis requires pitch, which armor stands cannot supply.

Boats can preserve pitch#

Boats preserve pitch. Wherever vertical components are needed, the reference entity must be a boat.

However, boat pitch cannot reach ±90°, so it cannot directly provide pure vertical vectors like (0, \pm1, 0). The community's solution is to use pitch \mp30^\circ, then cancel out the accompanying horizontal drift. Section 6.6 walks through this derivation.

Why 30 degrees specifically? Because \sin 30^\circ = \frac{1}{2}, making the vertical component a clean fraction of one-half, which yields clean numbers when paired with binary weights. Using 45 degrees yields \sin 45^\circ = 0.7071, making manual calculations much more cumbersome.

All selectors in Chapters 1 through 5 must include c=1 and should specify type=:

If a selector matches multiple entities, execution forks along multiple branches, running the command multiple times. Each CCT command is designed to output exactly one point; unintended branching produces scrambled results. Chapter 2　How CCT Works#

This chapter explains why traversing along a view rotation paired with a large distance computes precise geometric ratio points.

2.1 What facing actually does#

Let current position be P and target be Q. When facing is executed, orientation points toward Q. Traversing d blocks:

places execution at a point starting from P toward Q of length exactly d.

Regardless of whether P and Q are 3 blocks or 3000 blocks apart, facing normalizes the displacement vector (Q - P) into a unit vector of length 1.

Example: P is at (0,0,0) and Q is at (3,0,4), with distance \sqrt{9+16}=5. After facing, moving 1 block reaches (0.6, 0, 0.8)—exactly (3,0,4) divided by 5. Moving 10 blocks reaches (6,0,8).

This provides an inherent division operation. Each component of the direction vector is \frac{\text{original component}}{\text{total length}}. CCT is built around designing this division: to calculate a desired value, we structure right triangles so the denominator equals the desired divisor.

2.2 Finding midpoints with similar triangles#

Let S and M be two points at identical height separated by horizontal distance D. We want their midpoint.

  1. Step 1: Elevate the origin above S by distance H to S′.
  2. Step 2: From S′, look at M. The line of sight forms the hypotenuse:
    L = \sqrt{H^2 + D^2}
  3. Step 3: Advance H/2 along the hypotenuse.
    The small triangle formed is similar to \triangle S'SM with similarity ratio \frac{H/2}{L}.
    Horizontal movement:
    \Delta x = \frac{H/2}{L}\times D = \frac{HD}{2L}

    Vertical descent:
    \Delta y_{\text{drop}} = \frac{H/2}{L}\times H = \frac{H^2}{2L}
  4. Step 4: When H \gg D:
    L = \sqrt{H^2+D^2} = H\sqrt{1+\frac{D^2}{H^2}} \approx H

    Substituting into the horizontal displacement:
    \Delta x \approx \frac{HD}{2H} = \frac{D}{2}

    This is exactly half the horizontal distance. The midpoint is found.
    The vertical drop is \frac{H^2}{2H} = H/2, so descending by relative coordinate H/2 returns exactly to the starting height.

Numerical Example:
H = 100000, D = 20:

L = \sqrt{100000^2+20^2} = \sqrt{10000000400} \approx 100000.002

Advancing 50000 blocks yields horizontal displacement:
50000\times\frac{20}{100000.002} = 9.9999998

The error is roughly 1 part in 20 million compared to the ideal value 10.

Generalizing to Arbitrary Ratios:
Replacing H/2 with tH:

\text{Horizontal forward: } \frac{tHD}{L} \approx tD, \qquad \text{Vertical drop: } \approx tH

\boxed{\text{Forward} = tH, \qquad \text{Compensate Drop} = (1-t)H}

2.3 Why it was called the "Large-Number Compass"#

We use a fixed large distance H as a radial baseline, locating points by rotating directions and cutting lengths—matching straightedge-and-compass geometry. Because the approximation L \approx H requires H \gg D, H must be far larger than the figure's scale.

2.4 Where error comes from#

CCT is an asymptotic numerical approximation. Expanding \sqrt{H^2+D^2} via (1+\varepsilon)^{-1/2} \approx 1 - \varepsilon/2:

\frac{tHD}{\sqrt{H^2+D^2}} \approx tD\left(1 - \frac{D^2}{2H^2}\right) = tD - \frac{tD^3}{2H^2}

Horizontal Truncation Error:

E_x \approx \frac{tD^3}{2H^2}

Vertical Truncation Error:

E_y \approx \frac{tD^2}{2H}

Key Properties:

  1. Horizontal error grows as the cube of distance D (D^3).
  2. Vertical error decays as 1/H, while horizontal error decays as 1/H^2. Vertical error decays slower and becomes noticeable first.

For t = 0.5, H = 100000:

DHorizontal Error E_xVertical Error E_y
101.3\times10^{-8}0.00025
1001.3\times10^{-5}0.025
10000.01252.5

2.5 How big should H be?#

Game coordinates use 32-bit floating point with fixed relative precision \varepsilon \approx 2^{-23}. Total error balances geometric truncation against floating-point roundoff:

E(H) \approx C_1\frac{r^2}{H} + C_2\varepsilon H

Error is minimized when both terms are equal:
H \sim \frac{r}{\sqrt{\varepsilon}} \approx 2900\,r

For structures spanning a few to dozens of blocks, H \in [1024, 16384] is optimal.

Synchronous Replacement Principle: When modifying H, all corresponding distances (H, tH, (1-t)H, 2H) across the formula must be updated simultaneously.

2.6 Summary#

CCT relies on the asymptotic approximation \sqrt{H^2+D^2} \approx H for H \gg D. It is an asymptotic approximation, and H must be chosen within an optimal range.

3.4 A core principle for modifying commands#

Inserting or deleting any subcommand alters the geometric balance across the chain; the entire sequence of compensation distances must be re-derived.

Never edit long commands by guesswork. Always return to the action list, verify displacements component by component, and translate back into subcommands.

Chapter 4　Advanced CCT#

4.1 Far-point reflection#

Mirrors a point across an arbitrary axis line passing through the origin.

Canonical Skeleton:

Command (H = 1024, horizontal axis using armor stand):

Mathematical Form:
Let origin be (0,0,0), point vector be \mathbf{p}, and axis unit vector be \mathbf{u}:

\mathbf{p}_H = \mathbf{p} + 2H\mathbf{u} - 2H\frac{\mathbf{p}+H\mathbf{u}}{\lVert\mathbf{p}+H\mathbf{u}\rVert}

As H \to \infty:
\mathbf{p}' = 2(\mathbf{u}\cdot\mathbf{p})\mathbf{u} - \mathbf{p}

The parallel component is preserved, while the perpendicular component is negated.

Invariant Distance Property:

\lVert\mathbf{p}'\rVert = \lVert\mathbf{p}\rVert

4.2 A complete manual calculation#

Let axis \mathbf{u} = (0,0,1), point \mathbf{p} = (3, 0, 5), H = 1024. Ideal reflection: (-3, 0, 5).

  1. Advance H: position becomes (3, 0, 1029). Length: \sqrt{9+1029^2} \approx 1029.004374.
  2. Face origin, advance 2H = 2048: displacement is -\frac{2048}{1029.004374}(3, 0, 1029) = (-5.97082, 0, -2047.99129).
  3. Restore axis, advance H = 1024: displacement is (0, 0, 1024).

Total final position:

X = 3 - 5.97082 = -2.97082, \quad Y = 0, \quad Z = 5 + 1024 - 2047.99129 + 1024 = 5.00871

Total error: \approx 0.0304. Theoretical error \frac{\lVert\mathbf{p}\rVert^2}{H} = \frac{34}{1024} = 0.0332.

Increasing H to 4096 yields total error 0.0076 (a 4-fold reduction), confirming E \propto 1/H.

4.5 Squaring#

Formula: (x,y,z) \to (x, y+x^2, z)

  1. facing 0 ~a ~: Direction \mathbf{F} = \frac{(-x, a, 0)}{s} where s = \sqrt{a^2+x^2}.
  2. positioned ^ ^ ^-a²: Displacement \Delta_1 = \left(\frac{a^2x}{s}, -\frac{a^3}{s}, 0\right).
  3. rotated ~180 ~: Inverts horizontal yaw components while leaving vertical pitch invariant: \mathbf{F}' = \left(\frac{x}{s}, \frac{a}{s}, 0\right).
  4. positioned ^ ^ ^-a²: Displacement \Delta_2 = \left(-\frac{a^2x}{s}, -\frac{a^3}{s}, 0\right).

Sum: \Delta x = 0, \Delta y = -\frac{2a^3}{s} \approx -2a^2 + x^2.

  1. positioned ~ ~2a² ~: Cancels -2a^2, leaving \Delta y = x^2.

Truncation error is O(x^4/a^2). Inputs must be scaled into a compact domain like [-1, 1] before computation.

Chapter 6　MEF: The n-ary Tree#

6.1 Origins of the name#

MEF (Multi-Execute Fork) is also known as the n-ary tree or conjugate bisection. Branching is not restricted to n=2; n=3 produces ternary trees, etc.

6.2 The forking mechanism#

When a selector in as, at, positioned as, rotated as, or facing entity matches T entities, the entire downstream execution chain runs T times independently.

Total leaf executions:

N = \prod_{j=1}^k n_j

In MEF, selectors must never include c=1.

6.3 Drawing a line: armor stands are sufficient#

Using two armor stands named A with yaws at 0 and 180, this generates 8 collinear points across [-7, 7] with uniform spacing \Delta = 2.

6.4 The binary weight formula#

To distribute 2^k points uniformly across [-L, L]:

w_j = L\cdot\frac{2^{k-1-j}}{2^k-1}, \qquad j = 0, 1, \ldots, k-1

Point spacing:
\Delta = \frac{2L}{2^k-1}

Chapter 7　CCT × MEF#

7.1 Division of labor#

MEF multiplies execution paths; CCT applies geometric transformations along each path.

7.2 The nested point lattice circle#

Based on the Inscribed Angle Theorem.

  • Center entity: a
  • Diameter endpoints: two entities named r at distance R from a.

Because directions are derived from relative entity positions rather than entity rotations, armor stands are sufficient even for drawing vertical circles.

7.5 Deconstructing unfamiliar commands#

  1. Check entity type: Boats indicate vertical pitch operations; armor stands indicate horizontal geometry or position-derived directions.
  2. Count selectors without c=1: Multiply entity counts across layers to find total points.
  3. Identify H, 2H, H triplets: These represent far-point reflections.
  4. Identify binary sequences (4, 2, 1, 0.5\dots): These are MEF weight layers.
  5. Identify halving angle sequences (45^\circ, 22.5^\circ\dots): These are rotation layers.
  6. Check rotated as overrides: Determine whether entity yaw or pitch is active.

7.6 Summary#

The Single Criterion for Entity Selection:

Does this command read a non-zero pitch directly from the entity?
If yes \to Must use boats.
If no \to Armor stands are sufficient.

Chapter 8　Extension: Algebraic Expression of CCT#

8.1 State and rotation matrices#

The state of an execute chain is:

\text{State} = (\mathbf{P}, \mathbf{R})

where \mathbf{P} = (x, y, z)^T and \mathbf{R} = [\mathbf{L} \quad \mathbf{U} \quad \mathbf{F}].

\mathbf{R} = \begin{bmatrix} \cos ry & -\sin rx\sin ry & -\cos rx\sin ry \\ 0 & \cos rx & -\sin rx \\ \sin ry & \sin rx\cos ry & \cos rx\cos ry \end{bmatrix}
\mathbf{L} = (\cos ry, 0, \sin ry)^T
\mathbf{U} = (-\sin rx\sin ry, \cos rx, \sin rx\cos ry)^T
\mathbf{F} = (-\cos rx\sin ry, -\sin rx, \cos rx\cos ry)^T

Algebraic proofs of the three rules:#

  1. \mathbf{L} has Y = 0 identically and contains no rx, proving local left is always horizontal.
  2. The Y component of \mathbf{F} is -\sin rx, depending only on pitch. Thus rotated ~180 ~ flips X and Z while leaving Y invariant.
  3. When rx = 0, \mathbf{F} = (-\sin ry, 0, \cos ry)^T, proving rotated ~ 0 flattens orientation horizontally.

Algebraic Proof of the Armor Stand Limitation:
Because an armor stand has rx = 0 identically, its forward and left vectors both have Y = 0. Thus, branching displacements along the Y axis using armor stands are strictly zero.

8.2 Algebraic forms of subcommands#

  • positioned ^a ^b ^c:
    \mathbf{P} \to \mathbf{P} + a\mathbf{L} + b\mathbf{U} + c\mathbf{F}
  • facing <target>:
    Sets \mathbf{v} = \mathbf{P}_{\text{target}} - \mathbf{P}, then:
    \mathbf{F} \to \frac{\mathbf{v}}{\lVert\mathbf{v}\rVert}, \qquad \mathbf{U} \to \frac{\mathbf{Y}-(\mathbf{Y}\cdot\mathbf{F})\mathbf{F}}{\lVert\mathbf{Y}-(\mathbf{Y}\cdot\mathbf{F})\mathbf{F}\rVert}, \qquad \mathbf{L} \to \mathbf{U}\times\mathbf{F}
  • rotated ~a ~b:
    \mathbf{R} \to \mathbf{R} \cdot M(a, b)

8.3 Rigorous derivation of far-point reflection#

For origin at (0,0,0), point \mathbf{p}, axis unit vector \mathbf{u}, and parameter H:

\mathbf{p}_H = \mathbf{p} + 2H\mathbf{u} - 2H\frac{\mathbf{p}+H\mathbf{u}}{\lVert\mathbf{p}+H\mathbf{u}\rVert}

Decomposing \mathbf{p} = (\mathbf{u}\cdot\mathbf{p})\mathbf{u} + \mathbf{w} where \mathbf{w} \perp \mathbf{u}:
\lim_{H\to\infty} \mathbf{p}_H = 2(\mathbf{u}\cdot\mathbf{p})\mathbf{u} - \mathbf{p}, \qquad S_\mathbf{u} = 2\mathbf{u}\mathbf{u}^T - I

8.4 What transformation is a reflection, really?#

\det(S_\mathbf{u}) = (+1)(-1)(-1) = +1

S_\mathbf{u} represents a 180^\circ rotation about axis \mathbf{u}.

Composition of two reflections:

R = S_\mathbf{v}S_\mathbf{u} \implies \text{Rotation by } 2\theta \text{ around axis } \mathbf{u}\times\mathbf{v}

8.5 Converting back to in-game angles#

ry = \operatorname{atan2}(\sin ry, \cos ry) \times \frac{180}{\pi}
rx = \operatorname{atan2}(\sin rx, \cos rx) \times \frac{180}{\pi}

8.6 Limits of the algebraic approach#

Algebraic formulas provide theoretical limits as H \to \infty. Practical deployment requires verifying whether required pitch angles can be represented by in-game entities.

Epilogue#

This text unifies two core disciplines:

CCT is built upon four fundamental actions:

  • positioned: Shift the virtual evaluation frame.
  • rotated: Transform the local coordinate basis.
  • facing: Normalize displacements into orientation vectors.
  • Large Number H: Approximate nonlinear radical normalizations into linear and quadratic relations.

MEF is encapsulated in a single principle:

A selector matching T entities forks downstream execution into T independent concurrent paths.

Three Bottom Lines:

  1. CCT is an asymptotic numerical approximation; MEF is exact. Adjust H for decimal deviations; inspect entity counts for structural integer errors.
  2. Armor stands do not preserve pitch; 3D spatial traversal cannot be achieved using armor stands alone. Wherever vertical components are needed, reference entities must be boats or use hardcoded angles.
  3. The criterion for entity selection is not "whether the final shape is 3D," but "whether the command reads a non-zero pitch directly from the entity." The nested circle draws vertical circles using armor stands because directions come from relative position differences; the 3D point cube requires boats because its vertical displacements originate directly from boat pitch.
